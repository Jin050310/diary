# Plan-Do-See 다이어리 (과제 6)

계획(Plan) → 실행(Do) → 회고(See) 데이터를 서버 DB에서 연결하는 다이어리입니다. 큰 프로젝트를 단계(할 일)로 쪼개고, 하는 일을 기록하며, 계획 대비 어느 쪽으로 빗나가는지 확인합니다.
**결과물:** https://diary-amber-mu.vercel.app · **소스:** https://github.com/Jin050310/diary
**로그인이 없습니다.** 링크를 아는 사람은 누구나 볼 수 있으므로, 남이 봐도 괜찮은 내용만 넣습니다(모든 화면 위에 안내가 표시됩니다). 접근 제어는 7번 과제에서 적용합니다.

## 화면
화면마다 위쪽에 "이 화면에서 무엇을 하나요"가 한 줄로 적혀 있고, 가장 중요한 것이 맨 위에 옵니다.

| 메뉴 | 하는 일 |
|---|---|
| 달력 | 월간 달력 격자(칸마다 그날 마감 할 일 이름·남은 개수·진행 중 프로젝트 색 점). 날짜를 누르면 오른쪽(모바일은 아래) 패널에서 그날 할 일을 **바로 체크·추가·수정·삭제**. 아래 **프로젝트 카드**에 진행 막대·마감까지 D-day·다음 할 일 |
| 할 일 | 검색 + **칩 버튼**(진행 중·오늘·기한 지남·완료·전체·마감 없음, 개수 표시)으로 거르기. 우선순위·태그·정렬은 "자세히"에. 정렬 기준은 화면에 글자로 표시. 생성·수정·완료·완료 취소·삭제 |
| 실행 기록 | "무슨 일을 했나요 → 얼마나 했나요(15분·30분·1시간… 버튼 또는 시각 직접 입력) → 막힌 점" 3단계. "저장하고 완료 처리" 지원. 날짜별 기록 목록, 완료 기록은 접어서 표시 |
| 진행 방향 | **결론 한 문장**(계획대로/앞섬/뒤처짐) + 요약 카드 + 다음에 할 일 + 계획·완료·쓴 시간 누적 그래프. 주별 추이·반복 패턴(예상 대비 실제, 막힘 낱말, 요일별 작업)·개선점 후보·개선점 효과 비교는 접어서 표시. 숫자를 누르면 회고의 근거 기록으로 이동 |
| 회고 | 기간(전체·최근 7일·이번 달·직접)과 프로젝트를 고르면 "할 일은 어땠나요?"(전체·완료·지연·막힘)와 "시간은 어땠나요?"(예상·실제·차이)를 집계. 숫자를 누르면 바로 아래에 근거 기록. 개선점 한 줄 → 다음 계획 |
| 내보내기 | 모든 데이터를 JSON 파일 하나로 내려받기 |
| 계획 상세 | 계획 수정 + 수정 전 값이 보존된 수정 이력, 회고에서 반영된 개선점 |

## 실행
```bash
npm install
cp .env.example .env.local   # DATABASE_URL 을 본인 값으로 (Supabase Transaction pooler, 포트 6543)
npm run db:migrate           # db/schema.sql 을 DB에 적용 (여러 번 실행해도 안전)
npm run dev                  # http://localhost:3000
```
`.env.local` 은 Git 에 올라가지 않습니다(`.gitignore`). 비밀번호·접속 문자열을 코드나 화면에 넣지 마세요.

## 데이터 규칙 (contracts/pds-schema-v2.json)
- 날짜(`YYYY-MM-DD`)는 시간대 변환 없이 그대로, 시각은 UTC 로 저장하고 화면은 한국 시간(Asia/Seoul)으로 표시
- 모든 시간 길이는 **분(minute)** 정수
- 계획 수정 → DB 트리거가 수정 전 값을 `plan_revisions` 에 보존 (이력은 수정 불가)
- 할 일 삭제 → 행은 남기고 `deleted_at` 표시만 (회고 근거 추적)
- 완료 → 멱등성 키 UNIQUE + "할 일당 유효한 완료 1건" 부분 UNIQUE (버튼 비활성화에 의존하지 않음)
- 개선점 한 건 → 다음 계획 하나에만 반영 (UNIQUE)

## 진행 방향 계산 (lib/directionCalc.ts)
DB 와 화면에서 분리한 순수 함수라, 값이 맞는지 정해 둔 예제로 그대로 검증합니다.
- **계획 대비 속도:** 오늘까지 마감인 할 일의 예상 시간 합 vs 완료한 할 일의 예상 시간 합 (± 30분이면 "계획대로")
- **추세:** 이미 끝난 최근 두 주의 "계획 − 실제" 부족분이 커지는지 줄어드는지
- **예상 정확도:** 끝났고 실행 기록이 있는 할 일의 (실제 합 ÷ 예상 합), 태그별로도 계산
- **제때 못 끝낸 비율:** 마감이 지난 할 일 중 아직 못 끝냈거나 마감 뒤에 끝낸 것
- **막힘 낱말:** 막힘 사유에서 조사를 대충 떼어 센 근사값(두 번 이상 반복된 것만)
- 개선점은 **후보**만 만들고, 저장은 사용자가 정합니다.

## 점검 스크립트
개발 서버를 켠 상태에서 실행합니다(계산 테스트는 서버·DB 불필요). 임시 데이터(`__test__`)를 만들었다가 끝나면 지웁니다.
```bash
npm run test:schema                      # 메모리 DB 로 스키마 규칙 (서버 불필요)
node scripts/test-contract.mjs           # 계약 파일 ↔ 실제 DB 일치
node scripts/test-tasks-api.mjs          # 할 일 CRUD·검색·필터·정렬·중복 완료 방지
node scripts/test-executions-api.mjs     # 실행 기록, 원래 계획 값 불변
node scripts/test-retro-api.mjs          # 회고 집계 정의·근거 일치·다음 계획
node scripts/test-direction-calc.mjs     # 진행 방향 계산을 손으로 구한 값과 대조 (Node 22.18+ : .ts 를 바로 불러옴)
node scripts/test-direction-api.mjs      # DB 에서 읽은 결과가 순수 계산과 같은지, 삭제·완료 취소 제외
node scripts/test-security.mjs           # XSS, 비밀값 노출 (npm run build 후 실행하면 빌드 산출물도 검사)
node scripts/cleanup-test-data.mjs       # 테스트가 중간에 멈춰 남은 임시 데이터 정리
```

## 알려진 한계
- 로그인·권한이 없습니다(7번 과제).
- 실행 기록은 화면에서 수정·삭제할 수 없습니다(추가만 가능).
- `postgres` 4.1.1 은 동시 쿼리 수가 연결 수 상한을 넘으면 멈추는 문제가 있어 `lib/db.ts` 에서 상한을 30 으로 둡니다.
- 개발 서버가 켜진 상태에서 `npm run build` 를 하거나, 빌드한 뒤 바로 `npm run dev` 를 켜면 페이지가 계속 새로고침될 수 있습니다. 개발 서버를 끄고 빌드한 뒤, `.next` 폴더를 지우고 다시 켜세요.
